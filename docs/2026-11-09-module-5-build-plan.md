## Section 1: Evaluating a deep agent (~45 min)

Goal: run the Module 2 measure → improve → re-measure cycle on the Module 4 deep agent.

1. **Setup.** Env check, `utils/langsmith_links.py` helpers.
2. **Target function.** Wraps `create_deep_support_agent()`. The dataset questions include the customer's email, but the deep agent takes a verified `customer_id` from run context and redacts emails. The target looks up the email in the database and passes `SupportContext(customer_id=...)`, the way the app would after sign-in. This step is itself a teaching point: evaluating a harness means reproducing how the app calls it.
3. **Baseline experiment.** Module 2's 12-question `baseline_dataset.json` with `correctness_evaluator` and `count_total_tool_calls_evaluator`. Link to the experiment.
4. **Trajectory evaluators** (new, trace-based):
   - `specialist_routing`: was the expected specialist called (order vs product-policy), from the `task` tool calls
   - `subagent_dispatches`: how many delegations
   - `order_tool_calls`: tool calls inside the order specialist (this is where the rigid tools show up as inefficiency)
5. **Read the results in the UI.** Link to the experiment; find the order-specialist questions that take many rigid tool calls.
6. **Improve.** Rebuild with the scoped SQL order specialist and run experiment 2.
7. **Compare.** Link to the comparison view: correctness should hold, and tool calls should drop.
8. Optional: `with_verifier=True` (RubricMiddleware) as experiment 3, to compare quality gained against tokens and latency spent.

**Scoped SQL tool (security).** `customer_scope_guard` only checks `customer_id` and `order_id` arguments, so a raw `execute_sql(query)` would let a customer query anyone's orders. The tool must enforce scope itself. Options:
- (a) Run the query against temp views pre-filtered to the verified customer's rows (orders, order_items) plus the public products table. Recommended: the model still writes SQL, so the lesson holds.
- (b) Parse the query and reject it without a customer filter. Brittle.

Read-only connection either way. Add a Section 1 eval example that tries a cross-customer query, so the improvement is also checked for the leak.

## Section 2: Jev as a judge (~40 min)

Goal: when a cheap decision model can grade an agent, and how to check that before trusting it.

1. **Setup.** Recap of Jev from Module 4 S3 in one cell (it already covers `Noul`/`Choice`/`Score`); link back.
2. **Jev evaluator in code.** `utils/jev.py` plus one question, e.g. `Choice` with correct / partially correct / incorrect against the reference. Add as `jev_correctness_evaluator`.
3. **Score the Section 1 experiments** with `evaluate_existing` (no agent rerun). Link.
4. **Same evaluator in the UI.** Jevaluator setup steps (Gateway, `typesafe/jev-latest`, `/v1/systemone`), with a link to the evaluators page.
5. **Agreement on the human-labeled set.** `golden_set.json` has 30 agent outputs with `human_label` and a `bucket` (13 ok, 6 fabricated, 3 wrong, 3 numbers, 2 recited, 2 partial, 1 no_answer). Grade them with Jev, the aligned LLM judge from the Module 2 bonus, and the unaligned judge. Table: agreement with humans overall and per bucket, run-to-run variance over 5 repeats, cost, latency.
6. **Evaluate the tool gate.** About 20 labeled tool calls (side effect yes/no) → `JevToolGate` precision and recall at 0.5 / 0.7 / 0.9.
7. **Caveats.** Single narrow benchmark, cheap-but-wrong at scale, synthetic data only, pin the Jev version.

## Section 3: Harbor evals (~45 min)

Goal: evaluate in a fresh sandbox, for checks a dataset row can't express.

1. **Setup.** `uv sync --python 3.14`, `uv run mda evals init`, the harbor command with `--no-project` and `--env langsmith` (validated 2026-11-09).
2. **Anatomy of a task.** Brief, linking back to Module 6 §4: `Task.md`, `instruction.md`, `identity.json`, `task.toml`, Dockerfile, `tests/verify.py`; invalid vs failed.
3. **Run the three tasks from the notebook** (subprocess, streamed). Link to the experiment.
4. **Write a new task, hands-on.** Candidate: `refund-requires-approval` (the run must stop at the `request_refund` interrupt and never issue it). Fallback: a file the agent should write. Students fill in `instruction.md` and the verifier.
5. **See it fail.** Run against an agent with the guard removed (Tanmaiyii's Nov 3 test did this for cross-customer), see reward 0, restore, re-run.
6. **Read results in LangSmith.** `reward` and `harbor_error` feedback, linked to the trace. Fix the two gaps from the smoke test: verifier logs not downloaded, no model or token usage recorded.
7. **When to use which.** Harbor vs dataset table, with Section 1's experiment and the Harbor experiment side by side.

Agent under test: the managed agent through the MDA adapter (proven 2026-11-09). `--agent langgraph` on the Module 4 agent is a stretch goal: it needs identity passed in and a `result.json` the verifiers can read.

## Spike results (2026-11-09)

**Scoped SQL (Section 1): works.** `query_my_orders` plus `create_deep_support_agent(order_tools="sql")`, with 10 unittest cases for scope and bypass attempts (`tests/test_query_my_orders.py`). On the 12 baseline questions, one run each, judged by the unaligned `correctness_evaluator`:

| | rigid | sql |
|---|---|---|
| Correct | 4/12 | 7/12 |
| Tool calls | 132 (11.0/question) | 44 (3.7/question) |

The remaining failures are teaching material:
- The account phone/segment questions fail with rigid tools, since no tool reads the customer record. With SQL the agent masks the phone for privacy, which the reference doesn't expect: a harness vs dataset discussion.
- The Sony stock question fails in both. The product-policy specialist has no stock tool, and SQL missed the product name: a trace-reading exercise.
- The laptop return-policy answer fails in both because the unaligned judge penalizes extra detail: the setup for Section 2's aligned judge.
- One real SQL error: keyboard spend $623 vs $1,118.

Experiments: dataset `m5-spike-module2-baseline`, `m5-spike-rigid-*`, `m5-spike-sql-*`.

**Jev judge (Section 2): blocked.** Gateway returns 424 Failed Dependency: the workspace has no `TYPESAFE_API_KEY` provider secret. The spike script is ready. The target to compare against is the Module 2 bonus: LLM judge agreement with the 30 human labels was 73% (v0), 90% (v1), 97% (v2).

**Refund approval task (Section 3): works.** `managed_agent/evals/refund-requires-approval/` scored 1.0 with `interrupt_on={"request_refund": True}` (the run stops with no final answer) and 0.0 with `interrupt_on={}` (the agent says "I've submitted a refund request"). This is the "see it fail" demo for Section 3. The verifier was checked against paused, ran, and no-call fixtures. The verifier's stdout still isn't downloaded with `--env langsmith`, so only the reward is visible.
